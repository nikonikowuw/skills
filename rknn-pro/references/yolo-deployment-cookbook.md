# YOLO Series (YOLOv8 / YOLOv10 / YOLOv11 / RT-DETR) RKNN Deployment Cookbook

Version-aware workflow for exporting, quantizing, and deploying modern detection models on
RK3568, RK3576, and RK3588. Start from the official model-zoo path closest to the exact model family
and Toolkit2 release, then measure accuracy and latency against the original framework model.

---

## 1. Export Principles (Ultralytics → ONNX → RKNN)

### Export Rules
1. **Choose the output contract deliberately**: Rockchip model-zoo examples commonly expose raw
   detection branches and implement decode/NMS on the CPU. Do not blanket-remove every Sigmoid or
   decode node: compare the exact export graph, compiler mapping, accuracy, and postprocess contract.
2. **Opset version**: Treat 12 or 13 as conservative starting points, then verify the installed
   Toolkit2 operator list and conversion log.
3. **Static vs dynamic shape**: Prefer a static input shape for the first deployment baseline. If
   dynamic shapes are required, validate every supported shape and follow
   [memory-alignment.md](memory-alignment.md).

### Ultralytics Export (YOLOv8 / YOLOv11)

Two export paths exist, and they produce **different graphs**:

**Path A (recommended) — airockchip fork, raw multi-branch outputs.**
Many stock Ultralytics exports keep DFL/decode/concat operations in the graph and emit a single
`1x84x8400`-style output. To match the raw feature-map contract used by a corresponding
`rknn_model_zoo` C++ postprocessor, use
Rockchip's modified Ultralytics (`airockchip/ultralytics_yolov8`, which adds an RKNN-oriented
export mode), or the export scripts bundled with `airockchip/rknn_model_zoo` for your model
version:

```python
# Inside the airockchip ultralytics fork:
from ultralytics import YOLO
model = YOLO("yolov8n.pt")
model.export(format="rknn")   # emits raw per-branch outputs, no decode head
```

**Path B — stock Ultralytics export plus graph surgery.**
If you must start from a stock export, export static ONNX first, then trim the decode/postprocess
nodes yourself (see "Split the model" in [model-conversion.md](model-conversion.md)) so only the
backbone/head convolutions remain:

```python
from ultralytics import YOLO
model = YOLO("yolov8n.pt")
model.export(format="onnx", opset=13, simplify=True, dynamic=False, imgsz=[640, 640])
# Inspect the actual output contract before deciding whether graph trimming is beneficial.
```

Verify which graph you actually have by listing the ONNX outputs before converting.

## 2. Quantization Precision Optimization (INT8 Calibration)

YOLO models contain bottleneck layers (e.g., C2f / C3k2 modules, DFL convolutions) that can experience precision degradation under default INT8 quantization.

### A. Calibration Dataset (`dataset.txt`)
- Use **100–500 representative images** from the actual target domain.
- Do not use synthetic or all-zero images.
- Format `dataset.txt`:
  ```text
  ./calibration_data/000001.jpg
  ./calibration_data/000002.jpg
  ...
  ```

### B. Custom Quantization & Hybrid Precision
If mAP drops significantly after INT8 quantization, use accuracy analysis to find the sensitive
layers, then keep them in FP16 via the **official two-step hybrid-quantization workflow**
(`hybrid_quantization_step1` / `step2`). Toolkit2's `build()` has no custom-quantization-file
parameter — the layer list lives in the `.quantization.cfg` file that step1 generates. See
[npu-op-compatibility.md](npu-op-compatibility.md) for the full workflow and caveats.

#### Accuracy Diagnostic Script
```python
from rknn.api import RKNN

rknn = RKNN(verbose=True)
rknn.config(mean_values=[[0, 0, 0]], std_values=[[255, 255, 255]], target_platform="rk3588")
rknn.load_onnx(model="yolov8n.onnx")
rknn.build(do_quantization=True, dataset="dataset.txt")

# Run accuracy analysis to pinpoint low SNR layers
rknn.accuracy_analysis(inputs=["./calibration_data/000001.jpg"], output_dir="./accuracy_result")
```

#### Hybrid Precision (official two-step flow)
```python
# Step 1 — generate model.model / model.data / model.quantization.cfg
# (after config() and load_onnx(); proposal=True asks Toolkit2 to suggest float layers)
ret = rknn.hybrid_quantization_step1(dataset="dataset.txt", proposal=True)
```

Edit the generated `*.quantization.cfg` and move only the accuracy-critical layers (typically
neck / DFL / detection-head convolutions such as `/model.22/cv2.0/cv2.0.2/Conv`) to a supported
float type such as `float16`, keeping the rest INT8. Then build the artifact:

```python
ret = rknn.hybrid_quantization_step2(
    model_input="model.model",
    data_input="model.data",
    model_quantization_cfg="model.quantization.cfg",
)
```

File names and supported types are generated by the installed release — follow its bundled
`examples/functions/hybrid_quant` directory rather than hand-writing config formats.

## 3. Preprocessing Normalization

Standard Ultralytics YOLO models normalize RGB inputs with `norm_input = pixel / 255.0`
(zero mean, 255 scale).

In `rknn.config()`:
```python
rknn.config(
    mean_values=[[0, 0, 0]],
    std_values=[[255, 255, 255]],
    quantized_dtype="asymmetric_quantized-8",  # asymmetric quantization is recommended for YOLO
    quantized_algorithm="normal",
    target_platform="rk3588"
)
```

## 4. C++ Postprocessing and Output Handling

### Output Node Layout (YOLOv8 / YOLOv11)
For a standard 80-class 640x640 YOLOv8 model exported **without the decode head** (Path A in
Section 1), the raw outputs are 3 feature map levels:
- `stride 8`:  `1x(64 + 80)x80x80`
- `stride 16`: `1x(64 + 80)x40x40`
- `stride 32`: `1x(64 + 80)x20x20`

(Exact output count and channel order depend on the export script version — check the converted
model's output attrs with `rknn_query`. A single `1x84x8400` output usually indicates that at least
part of the decode/concatenation path remains in the graph; inspect the ONNX nodes rather than
inferring the exact boundary from shape alone.)

### Performance Best Practices in C++
1. **Measure native outputs**: Compare `want_float=0` plus manual dequantization with Runtime output
   conversion. For affine quantization use the queried `(value - zero_point) * scale` contract. If
   filtering before dequantization, convert the threshold into the quantized domain with checked
   rounding and saturation; do not compare raw integers to a floating-point confidence threshold.
2. **DFL Decoding**: Decode Softmax + DFL box coordinates only for candidates exceeding `conf_threshold`.
3. **NEON Acceleration**: On ARM Cortex-A76/A55, vector out class score multiplication and NMS bounding box distance math using ARM NEON intrinsics if post-processing takes > 2ms.
